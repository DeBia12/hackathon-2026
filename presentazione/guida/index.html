Far partire tutto

Tre comandi per avere l'ambiente in piedi. Il resto della guida spiega cosa ci fai dentro. 

# una volta sola: installa le dipendenze di app/ e agents/
npm run setup

# la web app su http://localhost:5173
npm run dev

# prima di ogni push: typecheck + lint + build
npm run check

Gli altri comandi, quando servono:

Comandi npm del progetto
ComandoCosa fa
npm run presentLe slide, su :8000
npm run guidaQuesta guida, su :8001
npm run db:upSupabase in locale (Podman, dentro WSL)
npm run db:downSpegne Supabase
npm run contrastoMisura il contrasto fra due colori

Se qualcosa non parte

npm run dev fallisce quasi sempre per lo stesso motivo: le dipendenze non sono installate. Lancia npm run setup. Per il database serve WSL con Podman attivo — se non ti serve persistenza, saltalo: la web app gira lo stesso.

Creare la web app

Vite + React 19 + TypeScript + Tailwind v4. Tutto il codice sta in app/, e @/ è l'alias per app/src/.

Dove sta cosa
PercorsoContenuto
app/src/App.tsxLa pagina principale
app/src/components/ui/I mattoni: Button, Card, Field
app/src/index.cssI colori e i font del brand
app/src/lib/Utilità e client Supabase

Aggiungere un componente

Non lo scrivi a mano: lo chiedi all'agente ui-builder, che conosce i token del brand e le regole di accessibilità. 

> usa ui-builder per una card con titolo, testo e un bottone "Scopri di più"

Ti restituisce un file in app/src/components/ui/ già conforme: HTML semantico, focus visibile, contrasti verificati. Poi lo importi: 

import { Card } from "@/components/ui/Card";

I colori: non scriverli a mano

I colori stanno in app/src/index.css dentro il blocco @theme, e li usi come classi Tailwind: bg-surface, text-ink, bg-accent-text. Sono presi dal sito Accenture vero, uno per uno.

L'unica regola che conta

Il brand ha due viola e due grigi, e il fondo decide quale usare. Su chiaro: text-accent-text e text-muted. Su scuro: text-accent-light e text-muted-dark. Scambiarli produce testo illeggibile — #A2A2A0 su bianco dà 2.56:1, sotto la soglia di 4.5:1.

Nel dubbio, misura invece di stimare: 

npm run contrasto '#BE82FF' '#000000'
→ 7.83:1 — AA PASS, AAA PASS

Le skill

Una skill è un foglio di istruzioni che Claude legge quando serve. Non esegue nulla da sola: cambia il modo in cui lavora.

Stanno in .claude/skills/, una cartella per skill con dentro un SKILL.md. Ne abbiamo 21: quattro scritte da noi, diciassette prese da un repository esterno.

Come si usano

Due modi. Le scrivi col nome preceduto da /, oppure non fai niente e Claude le apre da solo quando riconosce che servono. 

# esplicito
> /accenture-brand

# implicito: questa frase apre accenture-brand + accessibilita da sola
> fammi una landing page in stile Accenture

Gli agenti

Un agente è un Claude separato, con un mestiere solo e una memoria tutta sua.

La differenza con una skill è questa: la skill è conoscenza che entra nella conversazione in corso; l'agente è un esecutore che apre una conversazione nuova, fa il suo lavoro e ti riporta solo il risultato. Il tuo contesto resta pulito.

Stanno in .claude/agents/. Li chiami per nome: 

> usa revisore-accessibilita sulla pagina del questionario
Gli otto agenti disponibili
AgenteQuando usarlo
matt-implementer«Costruisci X» — un incarico intero, in un contesto separato
ui-builderServe un componente React
supabase-devServe una tabella, una query o una policy

Perché separati e non uno solo

Un agente che sa fare tutto sa fare tutto male. Ognuno di questi ha istruzioni strette e solo gli strumenti che gli servono: matt-reviewer, per dire, non può scrivere file — può solo leggere e giudicare. È questo che rende la sua review affidabile.

Gli hook

Skill e agenti vanno invocati. Gli hook no: sono script che scattano da soli, sempre, che a Claude faccia comodo o meno. Sono il livello più affidabile, perché non dipendono da una decisione.

I tre hook attivi
Quando scattaCosa fa
Prima di un git commitBlocca il commit se in stage c'è una credenziale
Dopo ogni modifica a un .tsxCerca violazioni di accessibilità certe e le fa correggere
A fine turnoLancia il typecheck: se fallisce, il turno non si chiude

Il codice è in .claude/hooks/, tre file da leggere in due minuti. Per disattivarne uno, togli la voce da .claude/settings.json.

Una giornata tipo

I comandi con lo slash stanno in .claude/commands/ e mettono in fila più passaggi. Questo è il giro completo, dall'inizio alla consegna.

  1. /kickoff — si parte Crea il branch, scrive il brief e registra la decisione architetturale in docs/decisioni.md.
  2. Si costruisce Chiedi quello che ti serve in italiano. Claude sceglie skill e agenti da solo. Se il lavoro è grosso e poco chiaro, /buildmatt lo spacca in ticket e li distribuisce.
  3. /audit — si verifica Audit di accessibilità sull'interfaccia. Da lanciare prima di dire «ho finito», non dopo.
  4. /ship — si consegna Esegue npm run check, poi committa e pusha. Se il check fallisce, non pusha.
  5. /demo — l'ultima ora Congela il codice, verifica che la demo parta e prepara il piano B.

La regola del progetto

Ogni decisione non ovvia va in docs/decisioni.md: una riga con cosa, perché, e cosa hai scartato. In questo hackathon la giuria guarda il processo più del risultato — quel file è il processo.

Tutti i file

L'intero progetto, cartella per cartella. Premi su un file per leggerlo.

L'elenco è generato da git ls-files, quindi è sempre allineato al repository vero: se un file esiste qui, esiste davvero. Si rigenera con npm run alberatura, e npm run guida lo fa da solo prima di aprire la pagina.
